# أساس نظام ترخيص مُشرِفي

الحالة: أُدمج أساس ترخيص Android في الفرع الأساسي `main`. اجتاز اختبار staging الأولي، لكن التفعيل برمز صالح والإصدار التجاري لم يُعتمدا بعد؛ لا توجد رموز تفعيل صالحة صادرة حالياً.

## حدود العمل الآمنة

- النسخة الأساسية المعتمدة للمشروع هي `main`، وتتضمن عميل Android ونظام الترخيص.
- لا يُعد APK الحالي إصداراً تجارياً نهائياً حتى يكتمل اختبار التفعيل الفعلي والتوقيع الدائم.
- واجهة الترخيص والتحقق موجودة في Android؛ نسخة الويب على GitHub Pages ليست محمية بهذا الترخيص.
- لا تُحذف قاعدة البيانات المحلية أو النسخ الاحتياطية عند انتهاء الترخيص أو تعذر التحقق.
- النطاق الأولي المقترح هو تطبيق Android APK. نسخة الويب على GitHub Pages لا تُعد محمية بهذا الترخيص ما لم تُصمم لها آلية مستقلة.

## المتطلبات المتفق عليها

1. ترخيص مستقل لكل هاتف.
2. التفعيل الأول يتطلب اتصالاً بالإنترنت.
3. بعد التفعيل يعمل التطبيق دون اتصال.
4. يعاد التحقق عند توفر الإنترنت كل 30 يوماً.
5. عند فشل الاتصال لا يتوقف التطبيق فوراً؛ توجد مهلة سماح.
6. انتهاء الترخيص أو تعليقه لا يمسح بيانات التلاميذ أو السجلات.
7. يجب السماح بتصدير النسخة الاحتياطية حتى عند انتهاء الترخيص.

## سياسة تشغيل مقترحة

- دورة التحقق: 30 يوماً من آخر تحقق ناجح.
- مهلة السماح المقترحة: 7 أيام إضافية عند تعذر الوصول إلى الخادم.
- لا تُعامل مشكلة الخادم أو انقطاع الشبكة كإلغاء للترخيص.
- بعد انتهاء المهلة دون تحقق: يتحول التطبيق إلى وضع محدود قابل للقراءة والتصدير، ولا تُحذف البيانات.
- الإلغاء الإداري الصريح يوقف العمليات التي تتطلب ترخيصاً، لكنه لا يمحو البيانات.
- يجب استخدام ساعة موثوقة من الخادم عند الاتصال، مع رصد رجوع ساعة الهاتف إلى الخلف دون إيقاف مفاجئ أو فقد بيانات.

## بنية الأمان المقترحة

### هوية الهاتف

- ينشئ التطبيق مفتاح توقيع خاصاً على الهاتف داخل Android Keystore.
- لا يُصدّر المفتاح الخاص ولا يُرسل إلى الخادم.
- يرسل التطبيق المفتاح العام فقط.
- يُربط الترخيص ببصمة المفتاح العام، لا برقم IMEI ولا بمعرّف قابل للتغيير وحده.
- إعادة تثبيت التطبيق أو تغيير الهاتف تتطلب سياسة استرداد/نقل ترخيص واضحة من لوحة المالك.

### التوقيع والتحقق

- يحتفظ الخادم بمفتاح التوقيع الخاص بالتراخيص في أسرار الخادم فقط.
- يتضمن التطبيق المفتاح العام للتحقق من توقيع الترخيص، ولا يتضمن مفتاح الخادم الخاص.
- الترخيص الموقّع يحتوي على: معرّف الترخيص، نوعه، تاريخ البداية، تاريخ الانتهاء إن وجد، بصمة مفتاح الهاتف، وقت آخر تحقق، وسياسة السماح.
- يتحقق التطبيق محلياً من التوقيع وبصمة الهاتف وتواريخ الصلاحية قبل اعتماد الترخيص دون اتصال.
- لا يكفي إخفاء رمز التفعيل داخل التطبيق أو وضع قائمة رموز في GitHub؛ ذلك قابل للاستخراج والنسخ.

### الخادم ولوحة المالك

يلزم خادم API وقاعدة بيانات ولوحة إدارة محمية بمصادقة قوية. الوظائف المطلوبة:
- إصدار رموز تفعيل عشوائية عالية القوة، وتخزين بصمتها فقط.
- تفعيل الرمز مرة واحدة وربطه بمفتاح هاتف واحد.
- عرض الأجهزة والتراخيص وتواريخ الانتهاء وآخر تحقق.
- تعليق الترخيص أو إلغاؤه أو تجديده.
- تسجيل عمليات الإدارة في سجل تدقيق.
- عدم وضع أسرار الخادم في المستودع أو APK أو ملفات الواجهة.

يوجد تنفيذ API باستخدام Cloudflare Workers مع D1 ضمن `licensing/worker/`. اجتاز اختبار staging الأولي تحدي الجهاز ورفض رمزاً غير معروف ومنع إعادة استخدام التحدي. لكن يجب التحقق من إعداد قاعدة D1 والأسرار ومفتاح التوقيع وإتمام تفعيل رمز صالح وتجديده وتعليقه قبل الاستخدام الفعلي.

## واجهات API المقترحة

- `POST /v1/activate`: يستقبل رمز التفعيل والمفتاح العام للجهاز ويعيد ترخيصاً موقّعاً بعد التأكد من أن الرمز صالح وغير مستعمل.
- `POST /v1/validate`: يتحقق من حالة الترخيص والجهاز ويعيد ترخيصاً موقّعاً محدثاً.
- `POST /v1/admin/licenses`: إصدار ترخيص من لوحة الإدارة بعد المصادقة.
- `POST /v1/admin/licenses/{id}/suspend`: تعليق ترخيص.
- `POST /v1/admin/licenses/{id}/renew`: تجديد ترخيص.
- `GET /v1/admin/licenses`: عرض التراخيص والأجهزة للمسؤول.

يجب أن تكون جميع الاتصالات عبر HTTPS، مع تحديد معدل الطلبات، والتحقق من صحة المدخلات، ومنع إعادة استخدام رمز التفعيل.

## بيانات الترخيص

الحقول المقترحة:
- `license_id`
- `activation_code_hash`
- `status`: issued / active / suspended / revoked / expired
- `license_type`: annual / perpetual / trial (حسب ما يقرره المالك)
- `starts_at`
- `expires_at` (فارغ للدائم)
- `device_public_key`
- `device_fingerprint`
- `activated_at`
- `last_validated_at`
- `created_at`, `updated_at`

## قرارات ما زالت مفتوحة

لم يُحسم بعد:
- هل سيُتاح اشتراك سنوي فقط أم سنوي ودائم؟
- هل توجد فترة تجريبية؟ وما مدتها؟
- هل يسمح بنقل الترخيص إلى هاتف بديل؟ وكم مرة؟
- هل يشمل الترخيص نسخة Android فقط أم نسخة الويب أيضاً؟
- اختيار مزود الخادم بعد تحديد حساب الاستضافة والميزانية.

يمكن بناء الهيكل التقني بحيث يدعم السنوي والدائم والتجريبي دون تفعيل أي خيار تجارياً قبل اعتماد المالك له.

## مراحل التنفيذ والاختبار

1. أُدمج عميل الترخيص في `main`، مع مفتاح جهاز داخل Android Keystore والتحقق من توقيع الترخيص.
2. أُضيفت خدمة Worker ومخطط D1 واختبار staging أولي.
3. اجتازت اختبارات CI الخاصة بالغياب والفروع ووضع القراءة فقط وسلامة النسخ الاحتياطي.
4. المتبقي: التحقق من إعداد D1 والأسرار ومطابقة المفتاح العام/الخاص، ثم اختبار تفعيل رمز صالح والتحقق والتجديد والتعليق على هاتف فعلي.
5. اختبار عدم المساس ببيانات التلاميذ والنسخ الاحتياطي والاستعادة في كل حالات الترخيص.
6. إصدار APK موقّع بالمفتاح الدائم بعد اجتياز الاختبارات؛ لا توزّع رموز تفعيل قبل ذلك.

## معيار القبول

لا يُعد النظام جاهزاً للبيع حتى تنجح اختبارات الخادم والتطبيق على هاتف فعلي، ويثبت أن نسخ رمز التفعيل إلى هاتف آخر لا يعمل، وأن انقطاع الإنترنت لا يعطل العمل ضمن السياسة، وأن انتهاء الترخيص لا يحذف أو يقفل تصدير البيانات.
